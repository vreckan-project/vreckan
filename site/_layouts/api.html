How requests are protected

Two orthogonal layers:

  1. Transport: every response carries the standard security headers (CSP, HSTS, X-Content-Type-Options, X-Frame-Options, Permissions-Policy, COEP, COOP, CORP) via a shared middleware. The collaboration-room and public-password pages use a per-response nonce CSP; proxied session traffic gets the looser session CSP.
  2. Authentication & E2EE:
    • Auth routes (/api/auth/*, handshake, public shares, the session-share public entry, room, session proxy, static) use plaintext bodies. The web-login credential is the vreckan_auth cookie (opaque server-issued token, 8 h TTL by default).
    • E2EE routes (catalog, launch, sessions, files, upload, homedirs, pinned, and all of /api/admin/*) require the same token and AES-256-GCM-encrypted request/response bodies. The client first runs the handshake (/api/handshake/*) to establish the per-session crypto key (RSA-PSS-signed nonce → RSA-OAEP key wrap → AES-GCM; the AAD binds the key to the session id, and X-Session-ID carries it).
    • Admin routes additionally enforce per-permission RBAC (18-permission catalog; the admin super-permission implies all). Auth-failure responses are deliberately plaintext in both ports (401 bypasses the E2EE wrapper).

Session reverse proxy (data plane) — session_proxy.rs

MethodPathHandlerAuth
ANY/api/apps/session/{session_id}/initial_session_authfirst hit: ?access_token= (the owner's token) is validated constant-time and exchanged for the vreckan_session_token_{id} cookie via a 303 to the same URL with the token stripped (the token is not consumed — replaying it re-sets the cookie); a valid collab or share-visit ?token= in the same URL additionally sets the collab_token_{id} cookie so the page's sub-requests authenticate by cookie
ANY/api/apps/session/{session_id}/{*path}session_proxy_subpathany admitted credential (below)

Admitted credentials (HTTP and WebSocket paths, both routes): the owner's session cookie; for collaboration sessions — and for plain sessions promoted to selkies secure mode by a session share — the collaboration token (the controller token or one of the viewers' tokens) presented via the collab_token_{id} cookie or a first-hit ?token=; and the per-visit tokens minted by session shares (the vreckan-side token map is the source of truth for tokens the container cannot know about). Anything else is 403 Forbidden: Invalid session or token. When the container runs in secure mode the proxy presents the request's own valid token to the upstream (falling back to the owner's container token for the owner), so each participant is individually authenticated by the container.

One any() registration per route handles both HTTP and WebSocket: an Upgrade header dispatches to the WebSocket bridge (client leg axum::ws, upstream leg tokio-tungstenite), everything else to the streaming HTTP proxy. Raw content-encoded bodies pass through undecoded; hop-by-hop headers are dropped; SameSite=None is set when the session page is opened embedded; the session CSP is applied to proxied responses. (Python registered the same surface as three routes — all-methods HTTP root, all-methods HTTP sub-path, and a separate WebSocket route — the consolidation is a representation difference, not a behavior change.)

Session shares — session_shares.rs

Owner-managed share links that let a session owner hand one of their running sessions — plain or room — to a recipient who has no Vreckan account, without sharing the owner's own credentials. Since v0.8.5 a link can also name an invited user with a Vreckan account: the invitee sees the session on the apps page and can Join it (the owner-grant gate above); a generic (unnamed) link only admits its holder through the link itself and does not light up the apps page. Each share has a role — full (input plus every file capability) or view_only (no input; browse and download on by default) — freely combinable file capabilities (file_browse, file_download, file_upload), an optional password, an optional expiry, and per-link revocation. The owner routes are E2EE-encrypted and owner-only; the public entry is plaintext and account-less.

DELETE /api/sessions/{session_id}/shares/{share_id} — revoke. Response 200: the revoked link's info (including invited_username), so the client can name who just lost access. Revocation marks the link dead (the public entry answers 410) and strips every per-visit token the link has ever minted — from the session's viewers list, the container's selkies token table, and the vreckan-side token map — without stopping the session. Since v0.8.5 the strip proceeds when the durable share row is missing, which is how the synthetic join grant (join:{username}, never a row in session_shares) reaches the same cleanup path. Revoking or expiring a named invite additionally strips the invitee's participant entry (the session-scoped strip of the synthetic join:{invitee} grant) — the invitee's apps-page row and join go dark at once.

Participants (v0.8.5, ANT-467). Every admitted visitor is recorded in the session's viewers list with how it got in; the two participant routes expose that to the owner.

DELETE /api/sessions/{session_id}/participants/{username} — revoke a single joiner: strips the joiner's token from the session's viewers list, the container's token table, and the vreckan-side token map, then persists the session. The joiner drops on the next proxy request; the session and everyone else's grants are untouched, and a later Join mints a fresh grant. Response 204 on success; 404 when that user holds no live join grant (never joined, already revoked, or the grant's TTL ran out).

Join grants carry a 24-hour TTL (JOIN_TTL_HOURS, fixed in v0.8.5) from the mint and from each (re-)join after a lapse — an expired entry is refreshed in place (same token, new expiry) rather than re-minted, and entries persisted before v0.8.5 pick the TTL up on their first post-upgrade (re-)join. The background sweeper (cleanup_expired_session_shares) strips expired join entries and prunes the in-memory token map of every expired record. The session list (GET /api/sessions) carries participants — the joiners' usernames — for the caller's own sessions only, so the UI can badge the count without a round trip.

Public entry. GET /share/{share_id}: 404 Share not found.; 410 when revoked, expired, or the session has ended; the public password page (200) when a password is set; otherwise a 303 redirect. POST /share/{share_id} (form field password): 303 on a correct password; the password page re-rendered with 401 on a wrong one; 400 when the share has no password. The 303 target:

Session kindRedirect
Room/room/{session_id}?token={visit_token}
Plain, promoted to secure mode/api/apps/session/{session_id}/?token={visit_token}
Plain, legacy container (no selkies token control plane), input onsame URL — the legacy default role is controller
Plain, legacy container, input offsame URL plus &role=viewer

Each visit mints a fresh per-visit token and records the visitor in the session's viewers list; the session proxy admits the token on every subsequent request and gates the in-container file API by the share's caps. A plain session is lazily promoted to selkies secure mode on its first share visit: a master_token is minted and the full token table is pushed to the container's /{session_id}/api/tokens; when that endpoint answers 404/401 or is unreachable (older selkies images without the control plane) the session stays legacy and the role rides the ?role= query parameter instead. A background sweeper removes expired shares on the share_cleanup_interval_seconds schedule and strips their tokens.

v0.8.1 hardening (F5/F6). The 303 answers from both public-entry routes carry Cache-Control: private, no-store, so a caching proxy cannot serve one visitor's per-visit token to another (F5). And the no-slash api/files root — which the container 301s to the slash-terminated listing — is on the browse side of the file-capability gate: a share visitor without the file-browse capability gets the browse 403 there instead of the previously un-gated 301 (F6).

Representation differences vs the Python original

Verified in the parity audit; none change functionality except where a gap is linked:

  • Multi-method routes collapse. axum registers get(...).post(...) on one path where Python used separate decorators per method — this is why the raw registration counts differ (119 Python route objects vs 104 Rust .route() calls at audit time; 112 in the current code) while the method+path surface is identical.
  • WebSocket handling differs by route. The session-proxy routes are any() and dispatch on the Upgrade header in-handler; the room WS route (/ws/room/{session_id}) is a plain GET upgrade.
  • Trailing slash on the /api/homedirs / /api/pinned collection roots (gap G7 in the port status document).
  • UUID path params. Python validated {session_id:uuid} at routing (malformed → 422); Rust matches any string and the handler fails later (gap G8).
